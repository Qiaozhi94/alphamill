## CI Verify

A task involving a git commit is not "done" when `git push` succeeds. It is
done when CI has actually finished and every job is green. Local checks
passing does not guarantee CI passes — different environment, different

1. Find the project's local check commands. Look in order: a project

2. Run those commands locally (lint, format check, type check, test suite —
   whatever the project defines). Fix everything before committing; don't

3. If a check tool is only loosely version-pinned in the project (e.g.
   `ruff>=0.6` with no upper bound), be aware the CI-installed version can
   differ from the locally-installed one and silently disagree — see the

### After pushing

1. Get the run for this push: `gh run list --limit 1` (or filter by branch/
   workflow if there could be ambiguity with concurrent pushes).
2. Watch it to completion: `gh run watch <run-id> --exit-status`. Do not

3. Confirm **every** job in the run succeeded, not just the one you expect
   to be affected by your change (e.g. a docs-only change can still break a
   job you didn't think to check).
4. If any job is red, treat the task as still in progress: read the failure
   log (`gh run view <run-id> --log-failed`), fix the root cause, commit,
   push, and repeat step 1–3. Only report the task complete once a run
   triggered by the current HEAD is fully green.

### Diagnostic tip: "local green, CI red, and the failure is unrelated to my diff"

This pattern usually means environment/dependency drift, not a bug in the
change just made. Before searching further:

- Compare the locally installed version of the failing tool against what
  the project's dependency file would resolve to fresh (e.g. `ruff --version`
  locally vs. the version range in `pyproject.toml`/`package.json`). CI
  typically does a clean install every run and will pick up new releases of
  loosely-pinned dev dependencies that a local environment — often installed
  once, months ago — never picked up.
- If that's the cause, the durable fix is to pin the dependency to a bounded
  range (not just a floor) in the project's manifest, verify locally with
  that exact version, and only then commit the pin change alongside any
  config adjustments the new version requires.

## CI Verify

A task involving a git commit is not "done" when `git push` succeeds. It is

### After pushing

1. Get the run for this push: `gh run list --limit 1` (or filter by branch/
   workflow if there could be ambiguity with concurrent pushes).
2. Watch it to completion: `gh run watch <run-id> --exit-status`. Do not

   push, and repeat step 1–3. Only report the task complete once a run
   triggered by the current HEAD is fully green.

### Diagnostic tip: "local green, CI red, and the failure is unrelated to my diff"

This pattern usually means environment/dependency drift, not a bug in the
change just made. Before searching further:

  the project's dependency file would resolve to fresh (e.g. `ruff --version`

  typically does a clean install every run and will pick up new releases of
  loosely-pinned dev dependencies that a local environment — often installed
  once, months ago — never picked up.
- If that's the cause, the durable fix is to pin the dependency to a bounded
  range (not just a floor) in the project's manifest, verify locally with
  that exact version, and only then commit the pin change alongside any
  config adjustments the new version requires.

## CI Verify

A task involving a git commit is not "done" when `git push` succeeds. It is
done when CI has actually finished and every job is green. Local checks

1. Find the project's local check commands. Look in order: a project

3. If a check tool is only loosely version-pinned in the project (e.g.

### After pushing

1. Get the run for this push: `gh run list --limit 1` (or filter by branch/
   workflow if there could be ambiguity with concurrent pushes).
2. Watch it to completion: `gh run watch <run-id> --exit-status`. Do not

   to be affected by your change (e.g. a docs-only change can still break a
   job you didn't think to check).
4. If any job is red, treat the task as still in progress: read the failure
   log (`gh run view <run-id> --log-failed`), fix the root cause, commit,
   push, and repeat step 1–3. Only report the task complete once a run
   triggered by the current HEAD is fully green.

### Diagnostic tip: "local green, CI red, and the failure is unrelated to my diff"

This pattern usually means environment/dependency drift, not a bug in the
change just made. Before searching further:

- Compare the locally installed version of the failing tool against what
  the project's dependency file would resolve to fresh (e.g. `ruff --version`
  locally vs. the version range in `pyproject.toml`/`package.json`). CI
  typically does a clean install every run and will pick up new releases of
  loosely-pinned dev dependencies that a local environment — often installed
  once, months ago — never picked up.
- If that's the cause, the durable fix is to pin the dependency to a bounded
  range (not just a floor) in the project's manifest, verify locally with
  that exact version, and only then commit the pin change alongside any
  config adjustments the new version requires.

## CI Verify

A task involving a git commit is not "done" when `git push` succeeds. It is
done when CI has actually finished and every job is green. Local checks
passing does not guarantee CI passes — different environment, different
dependency resolution, different tool versions.

### Before committing

1. Find the project's local check commands. Look in order: a project
   `CLAUDE.md`/`AGENTS.md`, `package.json` scripts, `Makefile`, or the CI
   workflow file itself (`.github/workflows/*.yml`, etc.) — the CI config is
   the ground truth for what "passing" means.
2. Run those commands locally (lint, format check, type check, test suite —
   whatever the project defines). Fix everything before committing; don't
   push speculatively and let CI find the problems.
3. If a check tool is only loosely version-pinned in the project (e.g.
   `ruff>=0.6` with no upper bound), be aware the CI-installed version can
   differ from the locally-installed one and silently disagree — see the
   diagnostic note below.

### After pushing

1. Get the run for this push: `gh run list --limit 1` (or filter by branch/
   workflow if there could be ambiguity with concurrent pushes).
2. Watch it to completion: `gh run watch <run-id> --exit-status`. Do not
   poll manually or guess — wait for the real result.
3. Confirm **every** job in the run succeeded, not just the one you expect
   to be affected by your change (e.g. a docs-only change can still break a
   job you didn't think to check).
4. If any job is red, treat the task as still in progress: read the failure
   log (`gh run view <run-id> --log-failed`), fix the root cause, commit,
   push, and repeat step 1–3. Only report the task complete once a run
   triggered by the current HEAD is fully green.

### Diagnostic tip: "local green, CI red, and the failure is unrelated to my diff"

This pattern usually means environment/dependency drift, not a bug in the
change just made. Before searching further:

- Compare the locally installed version of the failing tool against what
  the project's dependency file would resolve to fresh (e.g. `ruff --version`
  locally vs. the version range in `pyproject.toml`/`package.json`). CI
  typically does a clean install every run and will pick up new releases of
  loosely-pinned dev dependencies that a local environment — often installed
  once, months ago — never picked up.
- If that's the cause, the durable fix is to pin the dependency to a bounded
  range (not just a floor) in the project's manifest, verify locally with
  that exact version, and only then commit the pin change alongside any
  config adjustments the new version requires.
