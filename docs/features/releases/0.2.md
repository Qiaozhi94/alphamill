# v0.2 收口摘要

> 本文件记录 v0.2 已 `done` 的 Feature 交付内容。活跃 Feature 见 `BACKLOG.md`。

## F003：AlphaGen vendor 与可插拔生成器平面（2026-09-26 收口）

- **交付**：`factor_factory/generators/` 出现统一 `produce()` 接口与两个独立后端——AlphaGen RL
  主引擎（核心子集 vendor 进 `generators/alphagen_vendor/`，丢弃上游 requirements 改用本仓 pin）
  与人工 crypto 原生种子后端，换后端不改调用方；AlphaGen 的表达式 token 序列编译为标准
  `FactorDef.compute` 闭包（`generator="alphagen"`，表达式原文进 `meta["expression"]` 可反解）。
- **验收**：12 条 AC 全部勾选，引用的 11 个测试文件一次跑通 **163 passed / exit=0**；统一质量门
  `tools/verify.py` exit=0（1580 passed / 32 skipped / 1 xfailed）。产能 SC-003 由执行机 CUDA 下
  `registered ≥ 50` 断言锁定；边界 SC-004 由算子登记表、egress guard 与 `schema_version` 拒绝路径锁定。
- **夜槽与显存**（T033，执行机 `qiaozhi-lt` / RTX 4060 Laptop / 驱动 616.64）：
  `test_f003_kronos_lifecycle.py` 以 **0 xfailed** 通过（54 passed / 1 skipped），消费 F009 控制面
  真实卸载 Kronos；两次挖掘运行的 `kronos_offload` 读数 1.637 → 1.191 GB（`vram_released`），
  运行结束实例自动回到 `state=running`。
- **宇宙扩容对照**（T035）：基线 `sha256:d001fa0a…`（6 成员 / 湖内有效 3 对）与扩容
  `sha256:097bb31e…`（**52 成员** / 湖内有效 26 对）各跑一次，两次 completed/cuda、proposed 5 /
  registered 5、拒绝计数全 0。**候选质量差异在 CLI 路径上结构性不可观测**——`--generator` 只接受
  `manual`，该后端从固定假设集出候选、不读宇宙面板；AlphaGen 后端接入 CLI 已登记为 BACKLOG
  规划中的独立 Feature，是 AC-006 在真实挖掘产出上的验收载体。
- **已知缺口**：T035 原文要求 ≥30 对，台账 52 成员满足但**湖内有效仅 26 对**（`v2026.09.24` 导出
  只含现货，26 个 `-PERP` 成员湖内无分区）；`lake_tensor` 按 `universe_at()` 掩码，缺失 pair 不
  fail-closed，故运行成立而对数不达标，补齐需 F008 后续追加 PERP 导出。
- **顺带修掉的两个门禁缺陷**：`check_task_dag` 作用域纳入 `doc-reviewing`（检视整改引入的缺边
  过去要等流转后才判红，F009/F010 两次复现）；`validate_spec_lifecycle` 的路径判据改扩展名白名单
  （AC-010 正文的 `/health.device=cpu` 曾被当成绝对路径判红，与 `check_doc_consistency` 钉死的
  原文互相打架）。两处都配了先红后绿的回归测试与变异验证。

## F008：宇宙扩容与 point-in-time 宇宙台账（2026-09-25 收口）

- **交付**：研究宇宙从 6 对扩到 **35 对 ACTIVE**（40 对候选 − 5 对隔离），并新增只追加的
  `universe_membership` point-in-time 台账（70 行 = 35 对 × spot/perp），任一历史时点可用
  `universe_at(T)` 还原当时成员；冻结定义与台账 artifact 都是内容寻址的 canonical JSON
  （`sha256:05651fe0…`，70 条成员），供 F003 的 PIT 掩码与 F007 的 ResearchSnapshot 直接消费。
- **扩容执行**：两批回填（批 1 = 成交额前 30 含现有 6 对、批 2 = 第 31–40）逐对 `completed`；
  每批过质量门后准入（缺失率按**实际可得窗口**算，上线晚不算缺失）；**准入切换**=追赶回填
  （29 对 / 583,538 行）+ 补洞口（841 行）+ `deployment/.env` 的 `SYMBOLS` 6 → 35 对 +
  `--force-recreate` 采集容器（切换后 `symbols_ok=35 symbols_failed=0`，滞后 2–3 分钟）。
- **隔离的 5 对**：BANK/ONDO/PUMP/TUT（`missing_ratio_exceeded`）、TRUMP（`boundary_not_closed`）
  ——均为「定义里的 `listed_at` 取自永续上市日、门禁判的却是现货数据」这一已裁决口径问题所致，
  已立项为独立后续项（见 `BACKLOG.md`），本轮接受隔离结果。
- **容量实测（`AC-011`）**：全量导出（`--mode full --universe-filter`，未用 `--allow-shrink`）
  实测 **860 s**、湖 **30,028** 个分区文件 / **1,015 MB**、**36,794,805** 行；对照 6 对基线按
  对数线性外推（1,330 s / 51,468 文件 / 36,808,333 行）分别为 **0.65× / 0.58× / 1.00×**，
  远低于回顾裁决的判红阈值（1.5× / 1.3×）。NAS 备份实测见 `reports/f008/capacity-report.json`。
- **导出清单口径**：导出清单 = `universe_at(窗口终点)` ∩ 质量门 ACTIVE，且按 dataset 的
  `market_type` 命名空间求交；真实库 + 真实湖复核 35/35 逐对一致，`symbol_map` 保持全量。
- **执行机证据**：`reports/f008/执行机取证-T020-T023.md`（分片速率、两次事故归因、门禁与准入、
  T023 实跑、波次修复、`AC→证据` 映射）。
- **代码检视**：第 1 轮全量扫描 27 条（1 Critical / 7 High 全闭；7 组 Medium/Low 已立项
  `BACKLOG.md`「规划中」作为载体），issue 表与模式教训见 `docs/reviews/RETROSPECTIVE.md` 循环 20。
- **已知边界**：本轮消除的是**成员区间偏差**（何时进入/退出），不消除**成员选取前视**

  台账只追加的结构天然支持后续升级为逐期重算。见 spec §1 非目标与 `NFR-003`。

## F009：Kronos 服务生命周期控制面端点（2026-09-24 收口）

- **交付**：`kronos-signal-real` 暴露 `GET /lifecycle/status`、`POST /lifecycle/stop`、
  `POST /lifecycle/restore`，行为与架构 §7.1 动作表逐格一致：版本协商与单键错误信封、
  期望态 `desired` 与三值派生态（含 `transitional`）、单飞仲裁（`E_BUSY` 不排队）、
  `E_TIMEOUT` 表示"动作仍在进行"且不中断后台、失败落点按"不可逆的一步是否已发生"收敛。
- **本 feature 的真正增量**：`stopped` **待得住**——`desired=stopped` 期间推理端点不再隐式
  重载模型（走 F004 既有兜底路径、来源不标 `kronos`）。没有这一条，`stop` 之后任何一次
  `/predict` 都会把显存吃回去。
- **配套**：显存探测三级回退（不查 GPU 进程列表）与五个环境变量的值域/启动期判红；
  logfmt 结构化日志 + 超时后迟到完成的 `late_complete` 收尾行；控制面端口绑 `127.0.0.1`
  （同提交内迁移 F004 端口契约，原意不变）。
- **执行机证据**（`qiaozhi-lt`，CPU 实例）：契约套件 `--runxfail` 6 passed / **0 xfailed**；
  mock 实例三端点 404（新镜像带着控制面代码但不注册路由）；夜槽旅程 running → stop →
  5 次 `/predict` 全走兜底且 `model_loaded` 恒 false → restore → 恢复 `source=kronos`。
- **显存结论的边界**：`tests/integration/test_f009_vram_release.py` 以 `xfail(strict=True)`
  保持先红态——真实显存下降的取证与解除归 **F010**（其 AC-009/T011），两者不互相等待。
- **代码检视**：3 轮 10 条全闭（1 条修复引入、1 条规格自身不可满足经 owner 裁决拆边界），
  完整 issue 表与模式教训见 `docs/reviews/RETROSPECTIVE.md` 循环 19。收口 CI：35995587247。

## F010：Kronos GPU 推理基座（2026-09-25 收口）

- **交付**：`kronos-signal-real` 可在执行机以 CUDA 加载并产出真实信号。torch 的版本与 wheel
  索引由 Dockerfile 构建参数驱动（缺省仍是 `2.14.0` + CPU wheel，默认构建命令与落地前等价）；
  GPU 面（独立镜像标签、`cu130` 索引、`KRONOS_DEVICE: cuda`、nvidia × 1 设备预留、以
  `device` 以 `cuda` 开头为判据的 healthcheck）只在 `deployment/docker-compose.gpu.yml`
  叠加层出现，默认 compose 与 `.env.example` 未改。
- **失败可见**：显式 `KRONOS_DEVICE=cuda` 而拿不到 CUDA（CPU wheel 或无设备）时，启动、
  F009 `restore`、`/predict` 惰性加载共用的加载入口直接抛错，不静默回落 cpu；显式值只接受
  `cpu` / `cuda` / `cuda:0`。
- **执行机证据**（`qiaozhi-lt`，RTX 4060 Laptop / 驱动 616.64 / torch `2.14.0+cu130`）：
  `/health` 报 `device=cuda:0`、真实信号 `source=kronos`；常驻显存峰值 **565 MiB**（≤3GB 预算，
  不重标）；夜槽旅程 565 → `stop` → 137 MiB、整卡可用 7820 MiB ≥ 6GB → `restore` 恢复。
- **下游解锁**：`tests/integration/test_f009_vram_release.py` 的 `xfail(strict=True)` 已移除并
  真实通过（F009 AC-012）；F003 `vram_limit_gb` 缺省 6.0 与架构 §7.1 夜槽行均不重标。
- **运维前置**：执行机须装 nvidia-container-toolkit；构建用 host 网络 buildx builder；
  到 pypi.nvidia.com 不通时在本机 `deployment/.env` 给 `TORCH_EXTRA_INDEX_URL`
  （见 `docs/alphamill-integration.md` §七）。
- **代码检视**：3 轮 17 条全闭（7 条修复引入，含 1 条 High），完整 issue 表与模式教训见
  `docs/reviews/RETROSPECTIVE.md` 循环 20。PR #6 CI：36034315951。
